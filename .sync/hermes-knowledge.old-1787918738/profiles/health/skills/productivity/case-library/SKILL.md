# Case Library — курируемая база практических кейсов

## When to Use

- Игорь прислал ссылку → разбор в `expert-source-review` показал долгоживущую ценность.
- Запуск еженедельного cron-разбора свежих источников (`hermes-cases-weekly`).
- Поиск «как другие делали X» перед стартом новой задачи.
- НЕ для: одноразовых решений «берём/не берём» (это ACTIVE_TASKS, не case).

Не «хранилище всего подряд». Это **отфильтрованная долгоживущая база знаний**
о том, как люди реально применяют AI-агентов, с разбором применимости к нам.
Отличается от ACTIVE_TASKS тем, что ACTIVE_TASKS = бэклог реализации (временный),
а `docs/cases/` = справочник (постоянный).

## Когда использовать

- Игорь прислал ссылку на видео/статью/репо → разбор показал долгоживущий урок (не «берём на этой неделе»).
- Запуск еженедельного cron-разбора свежих источников (понедельник 9:00 МСК).
- Поиск «как другие делали X» перед стартом новой задачи.

## Структура

```
~/freelance-2026/docs/cases/
├── INDEX.md              # статусы всех кейсов, ссылки на файлы
├── codegraph.md          # один кейс = один файл
├── humanizer.md
└── ...
```

`INDEX.md` обновляется при каждом добавлении/пересмотре. Содержит 3 секции:
- **✅ Разобрано** — кейсы с практической ценностью, лежит one-pager
- **⏸ В очереди** — отложено, не разобрано до конца
- **❌ Пропущено** — отклонено (продающее, шум, дубль ADR), с короткой причиной

## Формат одного кейса (one-pager, ~150-300 строк)

```markdown
# <название> — <суть в 5-7 словах>

**Автор/источник:** <имя канала/автора> (<дата>, <URL>)
· repo <ссылка> · <звёзды>★ / <форки> форков · <активность> · <лицензия>

**Суть (2-3 строки):** что это, на чём, что делает.

**Стек:** технологии, языки, интеграции.

**Что применимо у нас:** [ДА/НЕТ/в очередь] — коротко с обоснованием.
Если закрывает наш ADR (например ADR-003 graph layer) — упомяни явно.

**Цифры/бенчмарки:** конкретные показатели автора + ссылка на источник.
**Обязательно верифицировать** через `curl api.github.com/repos/.../`
или другим независимым способом (см. L6 в `expert-source-review`).

**Trade-off (что автор сам признаёт):** честные ограничения.

**Сравнение с альтернативами:** 2-3 строки, как отличается от похожих.

**Действие:**
- [x] Создать запись (или: пропущено)
- [ ] Ссылка на ES-N в ACTIVE_TASKS если применимо
- [ ] Обновить наши ADR/правила если меняет архитектуру

**Подводные камни (из источника):** 3-5 пунктов — то, что автор сам
подчёркивает как «люди часто спотыкаются».

**Когда НЕ применять:** условия, при которых эффект нулевой или отрицательный.
```

## Процедура добавления (4 шага)

### 1. Реши: писать или нет
Триггер: разбор в `expert-source-review` показал долгоживущую ценность.
Если разбор чисто про «сегодняшнюю задачу» (взять/не взять) → только ACTIVE_TASKS.
Если инструмент/паттерн/источник → docs/cases/.

### 2. Создай файл кейса
По шаблону выше. Ссылка на источник обязательна. Звёзды/форки/дату последнего push
проверь живым API, не из видео.

### 3. Обнови INDEX.md
Добавь в секцию «✅ Разобрано» одну строку: название файла + автор/дата +
2-3 слова сути + «Закрывает наш ADR-N» если уместно.

### 4. Свяжи с ACTIVE_TASKS
Если из кейса вытекает пилот/реализация → ES-N в ACTIVE_TASKS со ссылкой
на файл кейса. Не дублируй содержание — только ссылка + план реализации.

## Еженедельный cron (уже настроен)

`hermes-cases-weekly`, понедельник 9:00 МСК, навык `expert-source-pipeline`.
Ищет 3-5 свежих публичных кейсов, разбирает по формату выше, кладёт в
`docs/cases/`, обновляет INDEX. Без автоматической реализации — только кейсы.

Источники для поиска (зашить в prompt крон-задачи):
- AI Stack Engineer (OpenCode, MCP, CodeGraph)
- Дмитрий Попов / COMANDOS AI (практика Hermes в бизнесе)
- vc.ru/ai (русскоязычные разборы)
- YouTube: фильтр «за неделю» + Hermes Agent
- GitHub: тренды в тематике ai-agents

## Pitfalls

- **Не смешивать с ACTIVE_TASKS.** ACTIVE_TASKS удаляются после реализации.
  docs/cases/ — навсегда. Если полезное лежит только в ACTIVE_TASKS и оно
  выполнено — через месяц никто не вспомнит.
- **Один кейс = один файл.** Не делать сборники «кейс 1, кейс 2, кейс 3»
  в одном файле. Каждый кейс ищется по названию, перелинковывается, решается
  отдельно жить или умереть.
- **Не писать то, что уже есть в ADR.** Если кейс подтверждает наш ADR — коротко
  укажи, не переписывай ADR в кейс-файл.
- **INDEX.md должен быть в 1 экран.** Если разросся — сократи до 1 строки на кейс,
  детали в файлах.
- **Не заливать продающее.** Канал с «рост от 30к до 2,5М» — не кейс, даже если
  тематически подходит. Пиши «продающее, пропущено» в секцию INDEX.
