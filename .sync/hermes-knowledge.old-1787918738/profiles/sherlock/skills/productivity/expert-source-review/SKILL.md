# Expert Source Review

Не «перескажи README». Это **экспертиза с действием на выходе**:
прочитай реальный код/контент → дай короткий вердикт → одобренное оформи как задачу.

## Когда вызывать

- Игорь кидает `@url:github.com/...` или `@url:youtube.com/...` с фразой «разбери»,
  «выступи экспертом», «насколько нам применимо», «прокачаем».
- Сравнение альтернатив («X vs Y, что нам подходит»).
- Не для: «как пользоваться», «найди мне», «сделай X» — другие задачи.

## Метод (5 шагов)

### 1. Разведка (2-4 параллельных web-вызова)

Один запрос на README/web_extract + один на список файлов (`api/repos/.../contents/`)
+ один на ключевые `.py`/`.md`/`.json` по необходимости. **Не читай весь README
целиком** — сначала структура, потом точечно по 2-3 ключевым файлам. Цель: понять,
как реально устроен проект, а не как автор его рекламирует.

### 2. Вердикт в формате 4 абзацев

**Жёстко: максимум 4 коротких абзаца. Без таблиц, без списков из 6 пунктов,
без «архитектурных уроков», без раздела «риски (экспертиза авг-2026)».**

- **Что это.** Одно предложение: что за штука, на чём написана, сколько звёзд.
- **Зачем.** Одно предложение: какую задачу решает, кому полезна.
- **Нужно ли нам.** Одно предложение с глаголом «берём / не берём / в очередь» и одной причиной.
- **Что с этим делать.** Либо «ничего», либо конкретный следующий шаг.

Если ролик/репо продающее и контента нет (общие фразы, обещания роста «до 2 тысяч 470»)
→ так и скажи: «продающее, шум, не берём». Не придумывай «полезные сигналы для нетворкинга»
чтобы оправдать запись.

### 3. Оформление в ACTIVE_TASKS.md (для одобренного)

```bash
cat >> ~/freelance-2026/ACTIVE_TASKS.md << 'EOF'

## 🧠 Эксперт-сессия (ДАТА) — одобрено к реализации в конце сессии

> Источники: <список с URL>

### 📌 ES-N. <название> (<автор/репо>) — <берём/в очередь/отклоняем>
- Что: <1 строка>
- Решение: <коротко почему>
- Что делать: <следующий шаг>

EOF
```

ID = ES-1, ES-2, … по порядку сессии. **Отклонённое тоже фиксируй** с пометкой
«ОТКЛОНЁН» — чтобы не возвращаться к тому же источнику через месяц.

### 4. Следующий источник = следующий вердикт

Завершил один → сразу спроси: «Следующий или закругляемся?»

### 5. Конец сессии: реализация

По команде «хватит, делаем» / «закругляемся» — реализуешь ES-N из секции
«Эксперт-сессия» по порядку. Каждую отмечаешь ✅, отчитываешься.

## Уроки этой сессии (HARD-WON — НЕ нарушать)

**L1. Стиль: 4 абзаца, не талмуд.** Игорь явно ругал: «слишком подробно, но непонятно,
куча терминов, и вообще непонятно что делать». Без таблиц, без длинных перечней рисков.

**L2. Workflow: одобрил → ACTIVE_TASKS → в конце сессии.** Игорь сам задал:
«сейчас мы это одобряем, ты записываешь как задачу этой сессии, а когда будем
заканчивать сессию — ты начнёшь реализовывать». **Не реализуй одобренное сразу**,
жди команды.

**L3. Отклонённое фиксируй тоже.** Через 3 месяца Игорь спросит «а что там с X» —
и сразу видно, что уже разобрали и отказались.

**L4. Продающее видео ≠ полезное видео.** Не выжимай «полезные сигналы для нетворкинга»
чтобы оправдать запись. Так и пиши: «продающее, шум».

**L5. Если URL битый/контент закрыт — скажи прямо.** YouTube 401, статья paywalled —
не выдумывай «что могло быть там». Скажи: «ссылка битая, контент недоступен».

**L6. Верифицируй громкие цифры.** Если источник заявляет «67k★», «62% экономии токенов»,
«200M пользователей» — проверь через `curl api.github.com/repos/<owner>/<repo>`
(поля: `stargazers_count`, `forks_count`, `archived`, `pushed_at`). Не доверяй README
на слово. Анти-авторитет из AGENTS.md применим и к звёздам, и к цифрам.

**L7. Долгоживущее → в `docs/cases/`, не только в ACTIVE_TASKS.** ACTIVE_TASKS — бэклог
реализации, временный. Если разбор содержит урок, применимый через год (новый инструмент,
паттерн, источник знаний) — кладём one-pager в `~/freelance-2026/docs/cases/` с INDEX.
В ACTIVE_TASKS — только ссылка на этот файл + план реализации. Это разные классы хранения.

**L8. Жёсткий бинарный гейт в конце рекомендации.** Игорь прямо запретил мягкое
«хочешь / не хочешь», «на твоё усмотрение», «рекомендую» — сочтёт размытым.
Любой вердикт/рекомендацию в дискуссии закрывай жёстким вопросом с явным выбором:
**«Принять? ДА / НЕТ»** (для ES — «брать / не брать»). Без развилок по желанию,
без «если хочешь». Исключение: Игорь ЯВНО делегировал решение
(«полагаюсь на тебя», «решай сам», «делай как знаешь») — тогда решай сам и ДЕЙСТВУЙ
без вопросов, не спрашивая подтверждения. (См. также: стиль речи в user-памяти.)

**L9. Делегированный вердикт = СВОЁ решение + аргументация, НЕ вопрос.** В режиме «Эксперт/Экспертная группа» Игорь часто говорит «мнение твое», «брать или нет — я полагаюсь на твоё мнение», «аргументируй», «полагаюсь на тебя» — это ЯВНАЯ делегация (см. L8). Рендери вердикт САМ: по каждой фиче жёсткое бинарное «берём / не берём» + одна причина + аргумент. НЕ закрывай гейт-вопросом («БЕРЁМ / НЕ БЕРЁМ?») — пользователь хочет решение и обоснование, а не вопрос. Паттерн 21.08.2026: первый проход закрывал каждый ES вопросом «брать / не брать?» → возврат «мнение твое … аргументируй» → исправлено решением-сам-и-записью. Решение принимаю я, сразу записываю в ACTIVE_TASKS (ES-N) + one-pager в `docs/cases/`, реализацию НЕ начинаю (жду «закругляемся» по L2).

**L10. Длинная статья приходит обрезанной — читай кэш целиком.** Attached context Хабра/длинных статей приходит с «[... middle omitted ...]» и пометой «Full text saved to: ~/.hermes/cache/web/<slug>.md». Середина часто несёт нагрузочную технику (точные модели, бенчмарки, failure-режимы, конкретные цифры) — вердикт по одному head+tail будет поверхностным. ЧИТАЙ кэш-файл целиком постранично: `read_file path="~/.hermes/cache/web/<slug>.md" offset=N limit=M` (файл большой, ~1800 строк, лимит 2000). Только после прочтения середины рендери вердикт. То же правило для любого источника с пометой «middle omitted / tail truncated».
