# Вердикт Femida — авто-классификатор входящих фич (Sinergy)

**Дата:** 2026-08-26 · **Профиль:** `femida` (юр-агент)
**Объект:** Архитектура авто-классификатора входящих фич: простая → игнор, сложная → Экспертный совет (6 профилей Hermes).
**Угол:** юридические риски — 152-ФЗ, лицензии компонентов, ToS провайдеров LLM, интеграция чужого OSS-кода.

> ⚠️ Не заменяет живого юриста для суда/РКН-разбирательства. Первичная экспертиза на базе действующего 152-ФЗ, КоАП, ГК РФ, GDPR и корпоративных ADR (002/003/004) + решения RW-4.

## 0. Что нашёл в коде (фактура, не догадки)

- `projects/sinergy/src/app/api/sinergy/classify/route.ts` (L74): классификация идеи → **`askGemini`** (Google Gemini, **США**, ход через прокси по ADR-002).
- `src/lib/sinergy/source-processor.ts` (L110): авто-парсинг Telegram/веб → **`askGemini`** (США). Сюда попадает сырой контент постов/страниц, часто содержащий ПДн (имена, контакты).
- Хранилище — **Supabase cloud** (`https://lufkysfjrdzfaxjbnkhi.supabase.co`, AWS/США), не РФ.
- `expert-council/route.ts` — **сейчас MOCK** (шаблоны, L140). Реальный fan-out на 6 профилей Hermes через `delegate_task` → OmniRoute → облачные LLM (США) **ещё не активен** → это проектный риск, не действующее нарушение.
- Зависимости классификатора: `zod`, `cheerio`, `supabase` — все MIT/Apache-2.0 (ок). AGPL в коде классификатора **пока нет**.

**Главный факт:** классификатор шлёт ВСЁ подряд в облако США и кладёт в БД за рубежом, **без предварительной фильтрации ПДн**. То есть даже если 99% фич — анонимные идеи, 1% с ПДн уходит тихо и незаконно.

## ВЕРДИКТ ПО ПУНКТАМ

### 1. ПДн входящих фич через LLM-классификатор и Совет — **РИСК (высокий, до исправления)**

- **152-ФЗ применим.** Любая автоматизированная обработка ПДн граждан РФ любым оператором — ст. 3, ст. 1 (оговорка «для личных/бытовых целей» ч.2 ст.1 не спасает, т.к. Sinergy — коммерческий сервис, вовлекает третьих лиц).
- **Локализация БД (ч.5 ст.18):** хранение ПДн граждан РФ — только на территории РФ. Supabase cloud (США) нарушает напрямую.
- **Трансграничная передача (ст.18, гл.12):** отправка текста фичи (с ПДн) в Gemini (США) = трансграничная передача → требует **уведомления Роскомнадзора + письменного согласия субъекта** на трансграничную передачу.
- **Иностранный оператор (ст.22.1, 266-ФЗ 2022):** Google как оператор ПДн обязан иметь РФ-представителя; при передаче туда мы перекладываем риск нарушения ст.22.1.
- **CLOUD Act / патриотические акты США:** доступ US-властей к данным на US-сервере подрывает гарантии прав субъектов — самостоятельное нарушение 152-ФЗ.
- **GDPR** (если субъект ЕС): прозрачность (Art.13), lawful basis, DPA с провайдером (Art.28), для США — SCC или сертификация DPF (Art.44–49).
- **Штрафы:** КоАП ст.13.11 ч.8 (юрлицо 30–50 тыс ₽, повтор — удвоение) + стек других частей + блокировка ресурса РКН (149-ФЗ) за не-локализацию.

**Можно ли слать ПДн в облачный LLM (Nous/OpenAI/Gemini)?** — **НЕТ** (строго, per 152-ФЗ + мои red lines).
**Локальные модели (llama.cpp / Ollama / OmniRoute-local)?** — **ДА, это compliant-путь.** ADR-004 уже закрепил local-first для приватных доков — распространить на классификатор и Совет, когда вход потенциально содержит ПДн.

### 2. Лицензии компонентов классификатора (AGPL vs MIT) — **РИСК (низкий сейчас, управляемый)**

- Текущие зависимости (zod/cheerio/supabase) — MIT/Apache-2.0 → коммерция ок.
- **AGPL-3.0 (§13, network-use clause):** если классификатор предлагается клиентам как сетевой сервис, встраивание AGPL-кода = обязательство открыть исходники всего производного. Sinergy — коммерческий продукт → **недопустимо** (решение RW-4: «AGPL — только внутреннее использование, не в клиентский продукт»).
- **MIT / Apache-2.0 / BSD** — безопасны, держать attribution.
- Риск активируется, если возьмём «готовый фреймворк классификации» под AGPL (напр. некоторые RAG/embedding-стековые либы).

### 3. ToS провайдеров LLM (авто-роутинг/классификация) — **РИСК (средний, процедурный)**

- Платные API-тарифы (Gemini API, OpenAI, Anthropic) **разрешают** автоматизированную классификацию/роутинг контента — это назначение API.
- **НО:** бесплатные/исследовательские тарифы часто **запрещают коммерцию** → использовать только платные.
- **Обучение на выводе/входе:** провайдеры могут использовать данные API для дообучения моделей, если не выключить (zero-data-retention / data-residency / opt-out). Для ПДн это усугубляет нарушение п.1.
- **Прозрачность:** авто-обработка пользовательских submission третьей стороной (LLM) должна быть раскрыта в политике обработки ПДн (152-ФЗ ст.18.1; GDPR Art.13) — «ваши данные обрабатываются сторонними ИИ-провайдерами».
- **ADR-002:** всё идёт через OmniRoute (прокси/хаб), а не напрямую к вендору → договорная связь с OmniRoute/Nous; проверить их ToS на субпроцессинг и ответственность за трансгранич (см. Orca-review: ToS провайдеров — целиком на Игоре).
- **Acceptable use:** не классифицировать контент запрещённых категорий (нелегальный контент) — нарушит ToS всех провайдеров.

### 4. Чужой OSS-код/репозитории как фичи — **РИСК (средний, при интеграции)**

- **GPL/LGPL/AGPL** в интегрируемом коде → обязательства copyleft при включении в Sinergy (коммерция): GPL — выпустить производное под GPL; AGPL — сетевой clause (RW-4).
- **MIT/Apache/BSD** — ок, с attribution.
- Анализ чужого репозитория через LLM **сам по себе не нарушает** лицензию (анализ ≠ распространение). Риск — если сгенерированный код **воспроизводит** чужой защищённый код (производное произведение, ст.1270 ГК РФ / РИД ст.1298/1373).
- Чужой **проприетарный/секретный** код, присланный как «фича» — конфиденциальность + потенциально ПДн → нельзя в облако (п.1).
- **Нужен license-gate:** когда классификатор помечает фичу «интегрировать OSS-либу X», до принятия — автоматическая проверка лицензии (Defender/Femida в Совете должны флагать лицензию для code-integration фич).

## ЧТО ДЕЛАТЬ / НЕ ДЕЛАТЬ

**ДЕЛАТЬ:**
1. **PDn-pre-screen перед любым вызовом облачного LLM.** Детектор (regex + локальная модель) email/телефон/ФИО/паспортные данные в `title/description/interview_answers` и сыром scrape-контенте. Нашёл ПДн → (а) обезличить/редактировать, либо (б) роутить на **локальную модель** (Ollama/OmniRoute-local, ADR-004), либо (в) отклонить с логом.
2. **Локальный inference для всего, что может содержать ПДн** — классификатор и (будущий) Совет. Облако (Gemini/OmniRoute-US) — только для заведомо не-ПДн контента (публичные стартап-идеи без персоналий).
3. **БД ПДн — в РФ.** Supabase self-hosted на Timeweb/Selectel (как VPS шлюза по ES-N ADR) ИЛИ не хранить ПДн в Supabase вообще (только обезличенные метаданные). Ч.5 ст.18.
4. **Процедурный комплайенс**, если всё же оператор ПДн: уведомление РКН (ст.22) + публикация политики (ст.18.1) + согласие субъекта (ст.9) + механизм прав субъекта (ст.14–21) + меры безопасности (ст.19). При трансграничной передаче — уведомление + согласие на неё.
5. **SBOM + LICENSES файл** для классификатора; запрет AGPL в клиентском продукте (RW-4). Любую новую зависимость гнать через `scan_typosquat` (ADR-002 §3).
6. **ToS:** только платные тарифы LLM; выключить training-on-data (zero-retention); раскрыть третью сторону в политике (152-ФЗ ст.18.1 / GDPR Art.13).
7. **License-gate** для OSS-фич: автопроверка лицензии до интеграции; AGPL/GPL — в internal-only или отказ (RW-4).

**НЕ ДЕЛАТЬ:**
- ❌ Не слать ПДн в Nous/OpenAI/Gemini/любой US-LLM (п.1, red line).
- ❌ Не хранить ПДн в Supabase cloud (США) — ч.5 ст.18.
- ❌ Не встраивать AGPL-компоненты в клиентский Sinergy (RW-4, §13 AGPL).
- ❌ Не использовать бесплатные/исследовательские тарифы LLM для коммерческой классификации (ToS).
- ❌ Не «молча» прогонять пользовательские submission через сторонние LLM без раскрытия в политике.
- ❌ Не интегрировать OSS-код, не проверив лицензию (copyleft-ловушка).
- ❌ Не генерировать код, воспроизводящий чужой защищённый исходник (РИД, ст.1270 ГК).
