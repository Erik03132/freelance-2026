# Уроки проектирования Мультиагентного Telegram-шлюза (ES-N)

**Дата:** 2026-08-23  
**Проект:** `freelance-2026` / Hermes Gateway / Expert Council  
**Связанный ADR:** `vault/04-Decisions/2026-08-23-es-n-telegram-gateway-council.md`  

---

## 1. Single vs Multi-Bot архитектура
- **Проблема:** Запуск 6 отдельных процессов gateway на небольшом VPS (2 vCPU / 4 GB RAM) создает лишнюю нагрузку на оперативную память и усложняет мониторинг.
- **Решение:** 
  1. Либо единый бот-координатор (Chief) в Telegram с поддержкой супергруппы с топиками (форумами) или `@mention` маршрутизацией через `delegate_task`.
  2. Либо легковесные профили под управлением общего пула.
- **Вывод:** Координатор Chief экономит память и позволяет прозрачно собирать сводные ответы (Chief Summary) нескольких агентов в одном месте.

## 2. Изоляция контекста через SOUL.md
- **Проблема:** Смешивание юридических, маркетинговых и инженерных инструкций в одном промпте приводит к деградации качества и галлюцинациям.
- **Решение:** Каждый профиль имеет свой изолированный `SOUL.md` и набор скиллов (`sherlock`, `femida`, `defender`, `marketer`, `financier`, `health`).
- **Вывод:** Делегирование через чтение `SOUL.md` гарантирует строгое следование роли каждого эксперта.

## 3. Экономика вызовов Совета Экспертов (Cost Optimization)
- Запуск полного 6-ролевого Совета увеличивает потребление токенов в 6 раз.
- **Правило:** Полномасштабный совет вызывается только при стратегических решениях, оценке крупных офферов (>10 000 руб.) или по прямому триггеру «Совет Экспертов». Для рядовых задач используется одиночный профильный агент.
